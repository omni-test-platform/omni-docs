核心概念

内容状态：基于代码与文档整理，待产品负责人复核。

双模架构（路径 A/B/C）

路径用例来源执行方式运行时 AI 依赖
A手写 test_*.pypytest + drivers/ 引擎否
BAI 生成的 test_*.pypytest + drivers/ 引擎否
C*.yaml 声明式 SpecSpecCompiler + StepExecutor是（生成/自愈时）

A/B 共用 core/ 与 drivers/，由 StepMetaClass、CaseMetaClass 自动装饰；C 由 SpecCompiler 编译、StepExecutor 执行，步骤经 ActionAdapter 分发，不使用元类。

核心对象

对象定义载体
testcase最小执行单元testcase/test_*.py 或一条 YAML 配置
suite一次执行选择的用例集合testset XML、suite.yaml
executor执行步骤的组件BaseEngine、BaseStepExecutor、StepExecutor
plugin通过注册表或 entry_points 扩展的能力五组 omni_engine.*
specYAML 声明式用例steps、validate、extract
config运行配置settings.ini、testconf/testbed/testset XML

executor 分三层：BaseEngine 是引擎级执行器，按 step_type 负责一类测试；BaseStepExecutor 是 A/B 路径的步骤执行器；StepExecutor 是 C 路径的统一执行内核，ActionAdapter 把 YAML action 映射到具体实现。suite 的执行顺序由 testset 的 location 顺序或 suite.yaml 的 case_list 顺序决定；Spec 内部则按 depends_on 拓扑排序。

BaseEngine 生命周期

setup_class()  →  setup()  →  run_step()  →  teardown()  →  teardown_class()

setup_class、teardown_class 为类级钩子，setup、teardown 为实例级钩子，均可选重载。子类必须设置唯一的 step_type，并实现 run_step(step_data) -> StepResult。引擎还可重载四个 AI 扩展点：on_locator_failure、on_step_failure、on_assert_failure、on_data_prepare。

from omni.core.base import BaseEngine, StepResult
from omni.core.registry import EngineRegistry


@EngineRegistry.register("ECHO")
class EchoEngine(BaseEngine):
    step_type = "ECHO"

    def run_step(self, step_data):
        return StepResult(
            success=True,
            step_name="echo",
            step_type=self.step_type,
            data=step_data,
        )

StepResult

所有引擎的 run_step() 都返回同一结果类型：

字段类型说明
successbool步骤是否成功
step_namestr步骤名称
step_typestr步骤类型标识
statusAnyTestStatusEnum：passed/failed/error/skipped
dataAny原始数据，如响应对象
export_varsdict导出到上下文的变量
errorstr失败或异常信息
durationfloat执行耗时（秒）
ai_metaAIAnalysisMeta失败分类、根因、建议等

GlobalContext

GlobalContext 是全局单例，保存配置路径、报告路径与报告摘要，并暴露配置、环境、统计等服务。

from omni.context import GlobalContext

GlobalContext.test_conf_path = "./conf/debug.xml"
ctx = GlobalContext()
print(ctx.log_full_path)
print(ctx.allure_results_path)
print(GlobalContext.report_summary.id)

跨步骤变量通过 GlobalContext.register()、set()、get() 使用，实际委托给 ContextVarManager，基于 contextvars 保证线程与协程隔离。路径类属性应由框架根据 test_conf_path 推导，不建议在用例中直接改写。

Reporter

Reporter 是报告后端抽象，提供 step() 上下文、dynamic_title()、dynamic_description()、attach()、message()、finalize()。ReportManager 把事件广播给所有启用的报告器，因此同一次执行可以同时产出 Allure、RF 和日志 HTML。报告器负责产出结果，通知器负责在会话结束时按 notify_mode 发送摘要，两者职责分离。内建报告器按 settings.ini 的 [REPORT] 开关启停。

五类插件注册表

注册表entry_points 分组扩展对象
EngineRegistryomni_engine.plugins执行引擎
ExecutorRegistryomni_engine.executors步骤执行器
AdapterRegistryomni_engine.adaptersSpec 动作适配器
ReporterRegistryomni_engine.reporters报告器
NotifierRegistryomni_engine.notifiers通知通道

omni.core.plugin_manager.discover_all() 统一触发五组发现，发现过程幂等；插件可实现 on_load、on_unload，并用 __omni_compat__ 声明兼容版本。注册既可用 @Registry.register 装饰器，也可在插件包的 entry_points 中声明分组。

配置

默认配置在 omni/config/settings.ini，项目级 conf/settings.ini 覆盖同名项。A/B 路径的入口是 testconf XML，它引用 testbed 与 testset；C 路径在 YAML 的 env 中声明 base_url 和变量。优先级从低到高为 settings.ini、testconf、testbed、testset、CLI 参数、环境变量；CLI 与环境变量适合临时覆盖，长期配置应落在项目文件中。
