Spec 适配器

内容状态：基于代码与文档整理，待产品负责人复核。

路径 C 的 YAML Spec 通过 action 字段选择步骤实现。StepExecutor 执行步骤时调用 AdapterRegistry.get(step.action)，找到适配器后执行 adapter.execute(step, context)。要让自定义 action 可用，就实现一个 ActionAdapter。YAML 模型与 validate、extract 的用法见编写 Spec 用例。

基类与最小实现

from omni.core.base import StepResult
from omni.spec.adapters.base import ActionAdapter
from omni.spec.adapters.registry import AdapterRegistry
from omni.spec.executor.context import RunContext


@AdapterRegistry.register("upper")
class UpperAdapter(ActionAdapter):
    action_type = "upper"

    def execute(self, step, context: RunContext) -> StepResult:
        text = (step.request or {}).get("text", "")
        return StepResult(
            success=True,
            step_name=step.name,
            step_type=self.action_type,
            data={"text": text.upper()},
        )

action_type 是注册键，必须与 YAML 中 action 的值一致。execute() 的 step 是 SpecStep，常用字段有 name、action、request、data、command、script、sleep、validate 与 extract；context 是 RunContext，提供 variables、base_url、tenant、subsystem、cluster 等。变量解析可以用 omni.spec.variables.resolve_data()。

对应的 YAML：

name: "upper demo"
steps:
  - id: 1
    name: "转大写"
    action: upper
    request:
      text: "hello"

委托型适配器

如果适配器只是把 Spec 步骤转交给某个 Runner，可以继承 DelegatingAdapter，只实现 _convert_step()：

from omni.spec.adapters.base import DelegatingAdapter


@AdapterRegistry.register("mysql")
class MysqlAdapter(DelegatingAdapter):
    action_type = "mysql"
    _runner_module = "my_package.mysql_engine"
    _runner_name = "MysqlEngine"

    def _convert_step(self, spec_step, context):
        return {"sql": (spec_step.request or {}).get("sql", "")}

DelegatingAdapter.execute() 会先取得 Runner，再调用 runner.run_step(step_data)。Runner 可以写 runner_cls = MysqlEngine 直接引用，也可以用 _runner_module / _runner_name 延迟导入以避免循环依赖；如果 context.runner 已经是目标类型的实例，会优先复用。Runner 以无参方式创建，因此构造函数不要要求必填参数。

上下文与变量

RunContext 中的 variables 是跨步骤变量表，resolve_data() 会递归解析 ${var}、${step.<field>}、${ENV.X}，传入函数表时还支持 ${func()}；适配器应先用它解析 step.request，再执行实际动作。返回值中的 export_vars 会由 StepExecutor 合并进 context.variables，后续步骤直接用变量名引用。需要多租户或多子系统时，从 context.tenant、context.subsystem 与 context.resolve_subsystem_base_url() 取值，不要硬编码地址。

注册表与分发

AdapterRegistry 的分组是 omni_engine.adapters，发现时校验对象必须是 ActionAdapter 子类。StepExecutor 找不到适配器时返回失败结果，错误信息为 No adapter registered for action: <action>。适配器执行完成后，StepExecutor 继续处理 step.validate 与 step.extract，所以适配器本身只需返回 StepResult，不需要重复做断言与变量提取。

内置适配器的 action_type 包括：api、web、cli / shell、script、sleep、sql、grpc、ws、k8s、chaos、prometheus、performance / perf。新增 action 不要与这些键冲突；重复注册会覆盖并输出警告。

与步骤执行器的区别

维度步骤执行器Spec 适配器
所属路径A/B（pytest + ApiRunner）C（YAML Spec）
注册表ExecutorRegistryAdapterRegistry
输入TStep + dict 上下文SpecStep + RunContext
分发点ApiRunner.__run_step()StepExecutor._execute_step_inner()
适合API 用例中的原子步骤YAML 中的一种 action

如果同一能力既要供 YAML 使用、又要供 pytest 用例直接调用，推荐先实现引擎或执行器，再用薄适配器委托，避免维护两套逻辑。

entry_points 发布方式：

entry_points={
    "omni_engine.adapters": [
        "upper = my_package.adapters:UpperAdapter",
    ],
}

适配器同样以无参方式实例化；需要配置时从 context 或 GlobalContext 读取，不要依赖构造参数。需要在适配器内复用请求客户端时，优先从 context 获取，而不是每次新建。若适配器内部持有连接，应在每次 execute() 结束时释放，或复用 context 中已有的 Runner / 会话。
