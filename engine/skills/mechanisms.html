核心机制

内容状态：基于技能定义与引擎实现整理，待产品负责人复核。

Skills 体系不是“把提示词写长一点”，而是把测试工程流程拆成可验证的契约：每个阶段有固定输入、固定产物、固定质量门；Agent 只负责按契约推进。下面这些机制决定了它能否稳定落地。

1. 产物驱动的阶段状态机

阶段之间不传递进程内对象，只传递文件：

阶段 N 读取上游文件 → 执行 → 写出本阶段文件 → 阶段 N+1 读取

由此得到三个性质：

  • 可续跑：会话中断、Agent 重启或人工介入后，只要上游文件还在，就能从失败阶段继续。
  • 可审计：每个阶段的输入与输出都能在 Git 历史中复查，评审不依赖聊天记录。
  • 可替换：某一阶段可以由人手工完成，只要产物符合契约，后续阶段仍可继续。

代价是产物格式就是接口：csv 列顺序、docstring 结构、import-result.json 字段、用例ID 列都不能随意改。改契约要同步改上下游技能与校验规则。

2. 实测前置：对抗“看起来合理”的定位器

阶段 0 和阶段 1 都有一条硬性前置：必须实际访问页面并验证元素定位。

要求做法不满足时
页面可达Playwright 真实打开 URL，确认路由与登录态显式标注“环境不可达”，相关功能点 skip/xfail
元素真实从实际 DOM 抓取 selector 与文案不得凭截图/描述推测
可定位验证存在、唯一、可见、可交互标记“未验证”，不进入方案定稿
多实例列表行/弹窗给出稳定定位策略记录策略与适用范围
可追溯方案头部记录抓取时间、方式、结论视为未完成

这条前置是整条链路最有效的质量杠杆：一个臆造的 selector 会在阶段 5 变成一批失败的自动化用例，而修复成本远高于在阶段 1 多打开一次页面。

3. 测试设计理论内建

阶段 1 不是“让模型随便想几条用例”，而是要求对每个功能点逐项套用测试设计方法：

方法作用典型产出
等价类划分合法/非法/边界输入分类有效类、无效类用例
边界值分析上下限与临界值最小值、最大值、上下溢出
错误推测空值、超长、特殊字符、格式错误异常输入用例
场景法主成功路径 + 备选/异常路径基本流、备选流、异常流
判定表/因果图多条件组合条件组合矩阵
状态迁移登录、会话、权限等有状态流程状态转换用例
正交实验参数多、组合爆炸代表性组合
异常/恢复网络中断、服务异常、刷新、重试容错与恢复用例

同时内建两条粒度约束，避免“层级很漂亮但用例很薄”：

  • 末级模块下应有多个功能点（不少于 2 个，分不同行）；只剩 1 个功能点时上提并入上一级。
  • 每个功能点在用例清单中应有多条用例（不少于 2 条）；只有 1 条时并入相邻功能点。

隐含需求（必填提示、长度限制、幂等、回车提交等）必须进入功能清单，并在备注列标注“隐含”，避免需求评审时被漏掉。

4. 单一结构骨架：子模块树

测试方案里的功能分级会直接派生成子模块树，并贯穿三处：

功能清单（一级/二级/三级/四级）
        │
        ▼
子模块树（一级为根，末级模块为叶子）
        │
        ├── csv「所属模块」：/登录/账号输入/必填校验
        ├── 禅道模块树：同名路径
        └── 自动化目录：testcase/login/form_validate/
              └── __init__.py: __module_zh__ = '03.表单校验'

规则：

  • 树根是一级功能；末级模块是叶子；叶子下用例不少于 2 条。
  • 节点路径就是 csv 的“所属模块”，也是禅道模块路径。
  • 一个或多个叶子可以聚合到同一个自动化子模块，但聚合关系必须在方案中注明，保证“方案 → 自动化”可追溯。
  • 新子模块必须写 __init__.py 并指定 __module_zh__；没有 __init__.py 的子模块视为未完成。

这套骨架的价值在于：测试方案、禅道用例、自动化目录不再各自维护一套结构，减少“方案叫 A、csv 叫 B、代码目录叫 C”的错位。

5. 全链路 ID 追溯

追溯链由四个关键字段串起来：

环节字段来源作用
禅道产品用例productCaseId阶段 3 导入结果禅道侧唯一标识
同步后 csv用例ID阶段 4 回写本地用例与禅道用例的映射
自动化 docstring禅道用例ID：<id>阶段 5 写入代码侧可读的追溯标记
执行报告pytest nodeid / case name阶段 6报告可回溯到用例与需求

完整链路：

PRD 需求/AC-xxx
  → testplan 功能点/用例
  → csv 行（所属模块 + 用例名称）
  → 禅道 productCaseId
  → 同步后 csv 用例ID
  → 自动化 docstring 禅道用例ID
  → pytest nodeid
  → Allure/JSON 报告

阶段 7 会检查 用例ID 是否非空、docstring 是否记录 ID、名称是否与 csv 一致。任何一个环节断链，都会在静态审查中暴露，而不是等到发布后靠人回忆。

当前实现的匹配键是用例名称，默认标题唯一。出现同名用例时，先消除歧义再回写；否则会出现错配或未匹配告警。

6. 幂等外部同步

禅道是外部系统，网络中断、权限变化、重复执行都很常见。技能包用三个设计降低同步风险：

  1. 先 dry-run：上传/导入/更新都支持只打印计划，不写数据。
  2. 判重键：模块按路径判重；用例库用例按“模块路径 + 用例名称”判重；导入按 fromCaseID + module 判重。
  3. 可重跑：已存在的自动跳过，只补缺失；单条失败不阻断整体，修正后重跑。

第一段上传还有一层“整表校验后 all-or-nothing”：空用例名、重复用例名、步骤/预期条数不一致、优先级非法等任一校验失败，直接终止，不会部分上传。这样不会留下“传了一半”的脏状态。

禅道 22.5 v2 REST 的已知坑

这些是实现层细节，维护技能脚本时需要知道：

现象原因处理

凭据只放在本地 admin profile 或环境变量中；不要写入技能文档、csv、日志或版本库。

7. 执行闭环与相关性回归

阶段 6 把“跑用例”扩展成四步闭环：

执行 → 分析报告 → 修复缺陷 → 相关性回归

失败归因

分类含义典型处理
BUG产品缺陷提交缺陷，保留失败用例
ENV环境/网络/服务不可用修复环境后重跑，不误判为产品问题
SCRIPT脚本定位、等待、断言或时序问题修脚本，补稳定性
DATA测试数据污染、重复运行冲突唯一命名、清理数据、独立构造前置
UNKNOWN证据不足保留原始日志，人工复核

相关性筛选

trigger_regression 的筛选逻辑：

  1. 从变更文件推断模块：取路径顶层目录作为模块名。
  2. 合并显式变更模块与变更子系统。
  3. 用例的 subsystem / module 命中变更模块/子系统，或 tags 与变更集合有交集，则选中。
  4. 没有变更信息，或筛选结果为空时，回退全量执行并告警。

回退全量是有意为之：漏跑一条相关用例的代价，通常高于多跑一批无关用例。告警让团队知道这次回归不是精确筛选。

trigger_regression 当前把筛选出的 path 交给 run_tests，因此只覆盖 Spec 路径；代码用例需要在 pytest 侧复用同一筛选结果。

失败归因的实战准则

以下经验来自实际项目执行，适合作为排查顺序：

  • 先隔离复现：全量失败但疑似时序/状态时，先单跑该用例。单跑通过、全量失败，多属时序/状态（SCRIPT）；单跑也失败，才倾向产品缺陷（BUG）。
  • 区分数据污染：创建类用例重复运行被“已存在”拦截，或断言命中上次遗留数据，属 DATA；用唯一命名/名称断言规避，不要先改产品。
  • 甄别 xpass：xfail 用例 xpass 时，检查是否弱断言命中了常显文案（假通过）；xfail 应保留并修正断言，不能仅因 xpass 就删除 xfail。

MCP 工具映射

安装 omni-engine[mcp] 后，Agent 可以通过 MCP 调用同一套能力：

工具作用委托
generate_case自然语言 → SpecSpecWriter
run_tests执行 Spec 用例StepExecutor
analyze_report提取失败用例与根因AIAnalyzer
fix_failure生成修复建议/补丁SpecHealer
trigger_regression相关性筛选并回归select_relevant_cases + StepExecutor

MCP 是薄门面，业务逻辑仍在 agents/core/AI/执行器中；未安装 MCP 时，CLI 与 Python API 提供等效能力。

“全流程自动化”的准确含义可以用自动化等级说明：

等级描述本项目
L0全手工：方案、用例、脚本、执行、报告都靠人传统方式
L1单点辅助：AI 生成片段、单条脚本或单次报告分析单点 AI 工具
L2阶段自动化 + 人工门：阶段自动执行，关键节点人工评审/确认Skills 体系当前定位
L3无人值守：无人工介入，自动处理需求变更与发布不作为当前承诺

把目标定在 L2 而不是 L3，是这套体系能落地的关键：机器负责重复劳动与一致性，人负责需求判断、风险接受与外部写入确认。

10. 适用边界

  • Agent 运行时：技能以 SKILL.md 形式加载；CLI 默认安装到 AtomCode 的技能目录，其他支持 SKILL.md 的 Agent 需按其加载规则安装。
  • 禅道可用：阶段 3/4 依赖禅道与 zentao-cli；没有禅道时可从阶段 5 开始，用 md/csv 作为用例来源，但会失去 ID 追溯。
  • 页面可达：阶段 0/1/5 依赖真实页面；SSO、验证码、MFA 等场景需要测试账号或可控的绕过策略，否则只能标记未验证。
  • LLM 可用：AI 生成/分析/自愈需要真实 LLM；未配置时部分组件降级为模板或关键词匹配，ai run 会直接失败。
  • 标题唯一：阶段 4 按用例名称匹配；同名用例需要先消除歧义。
  • 人工评审：PRD/设计、AI 产物、禅道写入、平台推送都保留人工关卡；不承诺无人值守。
  • 当前范围：技能家族以 Web UI 为主；API 域按同一命名约定预留 omni-api-*，尚未提供对应的完整技能链。
  • 不是调度器：omni-pipeline 由 Agent 按契约执行，不是后台 DAG 服务；定时、并发、环境租约由平台 AT 或 CI 负责。
