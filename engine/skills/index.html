Web 测试全流程自动化（Skills）

内容状态：基于 omni-engine 技能包与执行代码整理，待产品负责人复核。

核心优势

传统自动化测试的瓶颈通常不在“跑用例”，而在用例之前和之后：需求散落、测试方案靠人写、禅道用例与自动化脚本两套维护、失败后靠人判断、回归靠全量重跑。omni-engine 把这段流程做成了一套可执行的技能契约：

  • 一句话发起：给定需求 PRD、页面 URL 或接口地址，由 Agent 按依赖图推进后续阶段。
  • 阶段产物落盘：每个阶段输出固定格式的文件，下一阶段读取上游文件，不依赖会话记忆。
  • 全链路可追溯：禅道用例 ID 从 csv 传入自动化用例 docstring，执行报告中的用例可通过 docstring 或用例名回溯到禅道用例与需求。
  • 失败可续跑：任一阶段失败即停，修正后用 start 从失败阶段继续，不重跑已完成阶段。
  • 执行闭环：执行 → 报告分析 → 根因分类 → 修复建议 → 相关性回归，回到同一套 pytest / StepExecutor 能力。

这里的“全流程自动化”指阶段执行与产物流转自动化，不是无人值守：PRD/设计初稿、AI 生成用例、禅道写入与平台推送仍保留人工评审或确认。这是它能进入真实研发流程的前提。

前四层的职责边界（系统层是被测 Web、禅道与平台）：

层负责不负责
Agent理解目标、按技能契约调度、在人工关卡暂停不替代引擎执行用例
技能定义阶段输入/输出、步骤顺序、质量门与写作规范不是常驻服务，不保存进程内状态
工具真正执行 CLI、MCP 工具、禅道 API、pytest不决定流程走向
引擎执行、报告、回调、AI 分析与自愈不管理项目流程与评审

技能是“流程契约”，不是“脚本集合”。omni-pipeline 也是契约：由 Agent 按依赖图逐阶段调用，任一阶段失败即停；它不是后台 DAG 服务，也没有常驻调度进程。

两条自动化路径

引擎内有两条互补的自动化路径，适合不同阶段：

路径入口适合典型产物
webai 四 Agentwebai plan / testcase / generate / heal、webai run从 URL 快速探索、原型验证、临时回归测试大纲、用例 md、测试代码、修复报告
Skills 体系omni-pipeline 或分阶段技能需要禅道同步、用例 ID 追溯、质量门与平台推送的工程化流程方案、csv、同步后 csv、自动化用例、报告、审查结论

两条路径共用 Spec、StepExecutor、报告与回调能力，可以按阶段混用：例如先用 webai 探索页面，再用 omni-web-case-write 按工程规范补页面对象与用例。webai 的细节见 AI 能力。

与平台内 AT 的关系

Skills 体系不替代平台的自动化测试模块，两者分别处于“生产侧”和“管理侧”：

维度Skills 体系平台 AT
主要职责把需求/页面变成可执行、可追溯的用例与报告用例库、任务/计划、环境、Jenkins 调度、报告与门禁
运行位置开发者本机、CI、Agent 会话omni-server + worker + Jenkins agent
数据载体仓库文件（md/csv/py）与 Git 历史平台数据库与对象存储
追溯方式禅道用例 ID ↔ csv ↔ docstring ↔ 报告平台用例/任务/执行记录与禅道关联
衔接点omni-platform-case-push 推送用例元数据平台按任务/计划调度执行并回收结果

推荐做法是：在仓库里用 Skills 体系生产与维护用例，保持用例 ID 与文档可追溯；需要统一调度、环境治理、报告归档与质量门禁时，用 omni-platform-case-push 推送到平台，由平台执行。
