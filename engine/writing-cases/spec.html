Spec 用例

内容状态：基于代码与文档整理，待产品负责人复核。

Spec 是 omni-engine 的声明式路径（路径 C）。YAML 由 omni.spec.loader.load_spec() 解析为 TestSpec，SpecCompiler 校验依赖，StepExecutor 按步骤 action 查找 AdapterRegistry 中的适配器执行。Spec 不使用 TestCaseBase 与元类。

数据模型

层级字段
顶层name、id、risk、tags、metadata、env、data、steps
envbase_url、browser、variables、tenants、subsystems、headers
stepid（整数）、name、action、protocol、engine、request、data、command、script、navigate、validate、extract、depends_on、context、sleep

action 由适配器注册表决定，当前包括 api、web、cli/shell、script、sql、sleep、grpc、ws、k8s、chaos、prometheus、performance/perf。request 用于 api/web/sql/grpc/ws；data 用于 k8s/chaos/prometheus/performance；command 用于 cli/shell；script 用于内联 Python。

可运行示例

name: 变量与步骤编排
env:
  base_url: https://httpbin.org
  variables:
    greeting: hello
steps:
  - id: 1
    name: 生成结果
    action: script
    script: |
      __export__["answer"] = 42
  - id: 2
    name: 校验结果
    action: script
    script: |
      assert variables["answer"] == 42, variables
  - id: 3
    name: 输出信息
    action: cli
    command: 'echo spec-demo'
omni-engine-cli spec validate ./specs/demo.yaml
omni-engine-cli spec run ./specs/demo.yaml
omni-engine-cli spec compile ./specs/demo.yaml -o ./generated

spec run、spec validate、spec compile 的路径都是位置参数，不是 --spec。旧文档中的 spec run --spec <file> 会被当作未知选项。

变量与提取

变量支持 ${{ var }} 与 ${var} 两种方言，可引用 env.variables、环境变量 ${{ ENV.NAME }} 以及已提取的变量。extract 把结果写入后续步骤可用的变量：

steps:
  - id: 1
    name: 提取
    action: api
    request: {method: POST, url: /post, json: {user: demo}}
    extract:
      token: json.user

extract 默认按 JMESPath 解析；以 $.. 开头的表达式走 JSONPath。提取到的变量在后续步骤中以裸变量名引用，例如 ${{ token }}。旧文档中的 ${steps.1.token} 点路径形式在当前执行上下文中不一定存在，跨步骤引用建议使用裸变量名。

验证

validate 的每一项是以比较器为键的映射。比较器需要“路径 + 期望值”时使用列表形式：

validate:
  - equals: [status_code, 200]
  - contains: [body, "success"]
  - greater_than: [row_count, 0]
  - less_than: [p99_latency, 500]
  - semantic: "页面应显示欢迎语"
  - pod_phase: Running
  - deployment_ready: [ready_replicas, 2]

旧文档中的 - check: status_code / comparator: equals / expected: 200 三元组不会被当前 loader 识别，请改用上述写法。

执行顺序与并行

默认串行执行按 steps 的声明顺序进行；depends_on 在 StepExecutor(config={"max_workers": N}) 并行模式下用于 Kahn 分层，层内并行、层间按依赖顺序，循环依赖会抛出 SpecValidationError。CLI 的 spec run 使用默认串行模式，因此建议按依赖顺序书写步骤。

元数据与数据约束

metadata 使用统一的 CaseMetadata 契约，字段包括 name、priority（P0–P4）、tags、preconditions、tenant、subsystem、step_types。顶层 data 声明 DataConstraint，支持 type、source（ai_generated/csv/manual）、pattern、min_len、max_len、enum、file，供生成器与扩展读取；执行内核不会自动填充这些约束。

常见错误

  • id 必须是整数；重复或缺失会导致依赖排序与变量引用异常。
  • depends_on 引用不存在的步骤时，spec validate 会给出警告；并行模式下依赖环会直接报错。
  • action 未注册时返回 No adapter registered for action，检查是否拼写错误或未安装对应 extras。
  • cli 的 command 当前不做变量替换；需要变量时改用 script。
  • extract 路径未匹配时变量被跳过，后续步骤会读到空值；先用 spec run -v 逐步确认。

当前版本注意

当前工作版本中，validate 管道按 StepResult.data 取值；对 API 步骤，StepResult.data 与响应体的对应关系可能导致 status_code 等路径取到 None，从而把已成功执行的步骤判为失败；部分环境执行 API 步骤还可能报 _ApiRunner__config 未初始化。若遇到这些现象，先用 action: script 内的 assert 或 pytest/api run 通道验证；具体行为以当前版本为准。接口用例的其他写法见 API，执行参数见执行与编排。
