平台架构

内容状态：基于代码与配置整理，待产品负责人复核。

仓库职责

仓库定位主要技术运行产物
omni-server平台后端，模块化单体Go、Gin、GORM、Casbin、JWTAPI 服务（默认 8888）与 worker 后台进程
omni-web管理界面Vue 3、Vite、Naive UI、Pinia静态站点；开发态由 Vite 提供 9527
omni-enginepytest 执行引擎Python >= 3.9、pytest、Allure可独立使用的 CLI/库，也可由 Jenkins agent 调用
omni-deploy交付与部署编排Docker Compose、Nginx、Python 部署脚本容器编排、镜像构建、deploy.py systemd 部署
omni-license离线授权签发工具Go、RSA 2048、SHA-256单二进制 CLI + Web UI，产出 License JSON
omni-docs官方文档站VuePress 2、Markdown纯静态文档，不参与平台运行

omni-docs 只负责文档，不提供 API、不处理登录、不参与执行与授权；文档中出现的 9527/8888/3306 是产品组件的端口，不是文档站端口。

要点：

  • omni-server 与 omni-worker 共用同一镜像、不同入口；API 处理同步请求，worker 处理异步任务与定时调度。
  • 平台不直接执行测试；执行链路为 server → Jenkins → agent → omni-engine → 回调 server。
  • MySQL 8 是默认数据库；Redis、MongoDB 为可选项，不影响最小部署。
  • License 由独立工具签发，服务端内置公钥做本地验签，不依赖在线授权服务。

分层视角

展示层    omni-web：页面、路由、按钮权限
接入层    Nginx：静态资源 + /api 反向代理
应用层    omni-server Controller：HTTP、鉴权、参数校验
领域层    omni-server Service：业务编排、事务、跨模块协作
数据层    Repository → Entity → MySQL 8
执行层    Jenkins → Agent → omni-engine → 回调/进度

代码目录、模块依赖和调用链的细节见开发架构；本页只描述产品运行形态。

开发态与生产态

维度开发态生产态
启动方式run_server.bat、run_web.bat，或分别执行 Go/Vite 命令docker compose up -d --build，或 deploy.py 推送 systemd + Nginx
前端Vite 开发服务器，默认 9527，支持 HMR；API 直连 8888pnpm build 产物由 Nginx 托管，/api 同源反代
数据库debug 配置可用 SQLite，也可连本地 MySQL默认 MySQL 8，内嵌或外部实例
License可用 -tags licensefree 编译跳过校验必须导入有效 License，机器码需匹配
执行通道local / SSH / Jenkins 均可通常使用 Jenkins 通道与固定 agent
交付物源码与本地进程源码构建镜像或二进制；无官方镜像 pull 流程

生产部署的三种形态与参数见部署运维，版本与授权规则见版本与授权。
