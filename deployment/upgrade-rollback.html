升级与回滚

内容状态：基于代码与配置整理，待产品负责人复核。

升级前

  1. 阅读版本说明与兼容矩阵，确认数据库版本与运行时要求。
  2. 备份数据库与上传文件，见备份与恢复。
  3. 生产使用明确的 IMAGE_TAG，不要长期使用 latest。

Compose 升级

docker compose build
docker compose up -d
docker compose ps
curl -fsS http://<server-host>:8888/health

只升级后端：

docker compose up -d --build omni-server omni-worker

up -d 只重建镜像或配置变化的容器，--build 强制重新构建。升级后检查日志，确认迁移、License 校验与服务启动无错误：

docker compose logs --tail=200 omni-server

源码升级

python deploy.py -e <target-key> --only server,web,engine

复用已构建产物：

python deploy.py -e <target-key> --only server --skip-build

参数与动作见源码部署。

备份与失败回滚

deploy.py 在覆盖前为每个产物生成 .bak.<时间戳>，默认保留最近 3 份。

  • server：重启后 90 秒内必须 active，且 6 秒观察窗口内重启计数不变；否则打印 systemctl status 并自动恢复上一份二进制、再次重启。目标机原本没有二进制时无可用备份。
  • web：回填后校验 index.html，失败用 .bak 回填。
  • engine：安装后执行 omni-engine-cli --version 自检；失败只报错，不回滚 venv。

Compose 回滚依赖镜像标签：

IMAGE_TAG=<previous-tag> docker compose up -d --no-build

前提是上一版本镜像仍在本机。若升级时用 latest 覆盖，旧镜像已被替换，只能重新构建旧版本源码。

数据库结构变更

  • 每次启动都会执行 AutoMigrate，自动补建缺失的表、列与索引，幂等。
  • AutoMigrate 只加不删：删除列、改类型、改唯一键等破坏性变更必须由迁移脚本完成。
  • 升级后的新代码可能已写入新列；回退旧二进制前先评估兼容性。数据层回滚以备份恢复为准，不能用旧二进制“反向迁移”。
  • -init-db 每次启动都会执行种子注入，幂等；升级新增的菜单、字典由该参数补齐。

升级窗口检查

升级期间避免执行长任务；完成后观察 10 至 15 分钟，确认 omni-worker 正常消费、定时调度与 Jenkins 通道均正常，再恢复业务高峰流量。发现异常时优先回滚二进制或镜像，数据问题再按备份恢复处理。

验证

curl -fsS http://<server-host>:8888/health
docker compose logs --tail=200 omni-server | grep -iE 'migrate|error|license'

登录后抽查项目、AT 任务与报告页，并确认 omni-worker 正常消费后台任务。
