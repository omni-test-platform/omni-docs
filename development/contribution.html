贡献指南

内容状态：基于代码与文档整理，待产品负责人复核。

本页面向向 Omni 各仓库提交代码或文档的开发者。各仓库的 CLAUDE.md / AGENTS.md 是行为约束，本页只汇总跨仓库共同遵守的流程与验证口径。

分支与提交

  • 以仓库当前分支策略为准。本工作区当前位于 dev/v1.1.2；功能分支从开发分支切出，不直接在默认分支上提交。
  • 提交信息使用 Conventional Commits：type(scope): 中文描述，如 feat(at): 新增执行进度接口、fix(web): 修复用例列表筛选。
  • 常用 type：feat、fix、refactor、docs、test、chore；scope 用小写英文，如 server、web、engine、deploy、license、docs。
  • 必须让 pre-commit 钩子运行，禁止 --no-verify。钩子失败时修根因，不要跳过。
  • 一个提交只做一件事；不要夹带无关格式化或重构。多人共用工作区时，只暂存自己的改动块。

OpenSpec 变更

非平凡改动先在仓库 openspec/changes/<change-id>/ 下建立变更，至少包含：

文件内容
proposal.md为什么改、改什么、影响范围
design.md关键决策、备选方案、风险
tasks.md可勾选的任务清单与验证方式

实现过程中同步勾选任务；完成后按仓库的归档流程把变更移入归档目录。纯文案修正、依赖小版本升级等低风险改动可以不走变更，但要在提交信息中说明范围。跨仓库改动应在变更中列出受影响仓库与联调顺序。

各仓库验证

仓库最低验证
omni-servergo build ./...、go vet ./...、go test ./test/unit/...；涉及表结构时同时改实体与 migrations/ 脚本
omni-webpnpm typecheck、pnpm lint、pnpm build
omni-enginepytest tests；改版本号时同步 omni/config/version.py 与 CHANGELOG.md
omni-docspnpm build，检查导航/侧边栏路径存在、正文相对链接有效

数据库变更的硬规则：实体决定新库建成什么样，迁移脚本负责把老库升上去，两者缺一不可。脚本命名 YYYYMMDD_[模块]_[描述].sql，必须幂等，使用 MySQL/MariaDB 语法，并附执行前体检与执行后复核。只改实体不写脚本，线上升级才会暴露缺列。

文档贡献

  • 页面 frontmatter 必须包含 title、description、audience、status、since。
  • 正文内部链接用相对路径（./、../），不要写站点根绝对路径，保证历史快照不跳回最新版。
  • 未上线能力标“建设中”，不得用占位内容冒充已上线功能；draft 升 stable 需产品负责人确认。
  • 不写真实 IP、主机名、账号、密码、Token、私钥；示例统一用 <...> 占位。
  • 事实以代码与配置为准；与仓库旧文档冲突时，在页面中采用代码事实并备注差异。

提交前自检

  1. 改动是否只覆盖本次目标，是否夹带无关文件。
  2. 新增路由/菜单/i18n/按钮码是否前后端同时补齐。
  3. 是否更新了受影响的文档、CHANGELOG 与兼容矩阵。
  4. 是否运行了上表对应仓库的验证命令，并保留失败时的排查记录。
  5. 是否检查了敏感信息与调试残留。

版本与运行时要求见兼容矩阵，本地启动见本地开发。
